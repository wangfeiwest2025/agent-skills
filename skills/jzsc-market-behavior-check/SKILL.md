# 建筑市场行为检查（非现场）

对在建项目做「项目经理配备 + 安全员配备与归属」核查，输出可交付的检查报告。

## 核心能力与两个关键坑

### 坑 1：花名册 `.xls` 往往是假的

「合同用工备案花名册」从施工现场人员管理系统导出后，常被存成**扩展名 `.xls` 的 HTML 文件**。
判据：文件头是连续多个 `0D 0A`（空行），随后是 `<style type="text/css">` + `<table id="ids" class="zuobian">`。

```bash
head -c 16 "花名册.xls" | xxd   # 看到 0d0a 重复 ⇒ 是 HTML
```

后果：Excel/WPS 能打开，但 **pandas / xlrd / openpyxl 会报格式错误**。必须按文本走 HTML 解析。

表结构：标题「合同用工备案花名册」→ 按参建单位分块，每块 = 3 行头部
（`企业名称` / `合同名称`·`合同编号`·`备案人数`）+ 1 行 16 列表头 + N 行人员。
人员列序：序号/人员状态/姓名/性别/手机号码/人员类型/岗位工种/省份/身份证号/劳动合同号/
岗位证书号/是否普法培训/进场时间/退出时间/核酸检测情况/疫苗接种针数。

⚠️ `合同名称`/`合同编号`/`备案人数` 在**同一 `<tr>` 内是多个独立 `<td>`**，
不能把整行 join 后正则，要**逐单元格** `re.fullmatch`。

### 坑 2：查询平台是 LIKE 模糊匹配

查「张伟」会返回「张伟明 / 张伟华 / 王张伟」。**必须用「姓名 + 企业名称」双条件收紧**，
再在客户端做「姓名完全相等 + 企业名互相包含」过滤。

## 查询平台

### 北京市建设行业职业人员信息查询（主力，免登录免验证码）

入口：`http://bjjs.zjw.beijing.gov.cn/bjjs/sy/zwfw66/cxzx-sjzt/gcjsl/jsxyzyryxxcx58/index.shtml`

接口（GET / POST 均可）：

```
http://bjjs.zjw.beijing.gov.cn/eportal/ui?pageId=<pid>&currentPage=<n>&filter_LIKE_<字段>=<值>
```

| 页签 | pageId | 查什么 |
|---|---|---|
| **注册人员** | `53614300` | 一级/二级建造师、监理工程师、造价工程师 → **查项目经理** |
| **安管人员** | `53614302` | 安全生产考核合格证 A/B/C1/C2/C3 → **查安全员** |
| 施工现场专业人员 | `53614306` | 施工员、质检员、资料员等 |

字段名（从结果页 `<input id="filter_LIKE_xxx">` 读取）：

- 注册人员：`xm`(姓名) `zjhm`(身份证件号) `qymc`(企业名称) `zclx`(人员类型) `zcdj`(注册等级)
- 安管人员 / 专业人员：`workername`(姓名) `unitname`(企业名称) `postname`(人员类型) `workercertificatecode`(证件号) `certificatecode`(证书编号)

结果列：注册人员 = 序号/姓名/企业名称/人员类型/注册号/注册专业/有效期结束日期/许可机关；
安管人员 = 序号/姓名/企业名称/人员类型/证书编号/有效期结束日期/许可机关。

⚠️ **解析要点**：结果表 `<table class="xx">` 内数据行**缺少 `</tr>` 闭合标签**，
「序号」列由 JS 回填（服务端为空）。→ **不能按 `<tr>` 切分**，要取表内全部 `<td>`，
按表头 `<th>` 数量分块。见 `scripts/jzsc_query.py`。

### 全国建筑市场监管公共服务平台（四库一平台）

`https://jzsc.mohurd.gov.cn` 是纯前端 SPA，API 带签名校验（需动态 `v` 头），**无法直连取证**。
但北京市上述页面**已同步收录**其一级建造师、监理工程师、一级造价工程师注册数据（页面有明确提示），
所以**用北京市页面即可覆盖**，不必强攻四库一平台。需要人工核验时把 URL 给用户自行打开。

住建部安全生产考核信息平台 `zlaq.mohurd.gov.cn` 实测返回 521，同样交给用户浏览器访问。

## 检查标准：建质规〔2025〕3 号

《建筑施工企业、工程项目安全生产管理机构设置及安全生产管理人员配备办法》
（2025-09-26 发布，**2026-03-26 起施行**）。

获取正文：通知页 `https://www.mohurd.gov.cn/gongkai/zc/xzgfxwjk/art/2025/art_934265176.html`
正文在**附件 PDF** 里，需从页面 HTML 里抠出 `/api-gateway/jpaas-web-server/front/document/download?fileUrl=...`
链接后再下载（页面请求带 Referer），PDF 用 `pypdf` 提取文本。

**关键条款**

| 条款 | 内容 |
|---|---|
| 第二十条 | 项目经理是项目安全生产第一责任人 |
| 第二十一条 | 应配**项目安全总监**的门槛：现场人员峰值 >500 人 / 房屋建筑工程施工面积 >10 万㎡ / 市政合同价款 >4 亿元 |
| **第二十六条** | **施工总承包**配专职安全员：<br>· 建筑工程、装修工程按建筑面积：<1 万㎡ ≥1 人；1 万～5 万㎡ ≥2 人；>5 万㎡ ≥3 人，每增 5 万㎡ 至少加 1 人<br>· 市政基础设施按合同价款：<5000 万 ≥1 人；5000 万～2 亿 ≥2 人；>2 亿 ≥3 人，每增 2 亿至少加 1 人<br>· 涉及**建筑起重机械**的，另增 ≥1 名**机械类**专职安全员 |
| **第二十七条** | **分包企业**配专职安全员按施工人员数：<50 人 ≥1 人；50～200 人 ≥2 人；200 人以上 ≥3 人且不少于施工人员总数的 1% |
| 第十八条 | 企业层面：总承包特级 ≥6 人、一级 ≥4 人、二级以下 ≥3 人；专业承包一级 ≥3 人、二级以下 ≥2 人；劳务分包 ≥2 人 |

> 总包安全员档位需要**建筑面积**。花名册里没有这个数据 —— 必须在报告里列为「待补正项」，
> 并给出逐档结论（如「2 人 → 若 >5 万㎡ 则不达标」）。不要瞎猜面积。

## 判定逻辑（三分法）

对每个人按「姓名 + 企业名称」查本单位名下记录：

| 情形 | 判定 |
|---|---|
| **本单位名下有记录** | ✓ 本单位人员且持证 |
| 本单位名下无，但**按姓名全库检索**发现同类证书挂在**其他单位** | **✗ 证在他单位** → 疑似挂靠 / 非本单位人员 |
| 本单位名下无，且全库**无任何同名记录** | **✗ 无证**（重名率高的姓名要注明「建议核对身份证原件」） |

⚠️ **关键判读规则 —— 不要被同名噪音误导**：
「他单位记录」只有在**本单位名下 0 条**时才有意义。若本人**已在本单位查到有效证书**，
那么全库检索出的其他单位记录**基本是无关的同名他人**，不构成问题。
实测例：某总包单位的「甲某」本单位有 C3 证，同时能在另一家单位查到同名 C3；
另一位「乙某」有本单位 C3 证，同时能在第三家单位查到同名 B 证与二级建造师 —— 这些都是撞名，**不是挂靠**。
→ **先看本单位命中，命中就结案；只有本单位 0 条才去分析他单位记录。**

**项目经理**：总包必配；专业分包应有项目负责人。应查两项 ——
①**注册人员**库的建造师注册（含等级、专业、注册号、有效期）；②**安管人员**库的 **B 证**（登记为「项目负责人」）。

**安全员**：查**安管人员**库。A=企业主要负责人、B=项目负责人、C1=机械类、C2=土建类、C3=综合类。
专职安全生产管理人员应为 C 证。

**不适用**：监理/咨询单位不套用第二十六、二十七条（另行核总监理工程师）；劳务分包不强制配项目经理。

## 执行步骤

1. **解析花名册**：`python scripts/market_check.py <花名册目录> out.json`
   - 自动识别 HTML 伪装 xls；真 Excel 会提示先转换
   - 按合同编号后缀判类型：`ZB`=施工总承包、`ZY`=专业分包、`LW`=劳务分包、`JL`=监理
   - 岗位工种含「项目负责人/项目经理」→ 项目经理；含「安全」→ 安全管理人员
2. **平台核查**：脚本对每人做「本单位双条件 + 全库同名」两轮检索，产出三分判定
3. **数量核查**：按第二十六/二十七条对照每组安全员人数
4. **出报告**：按项目分节，含「问题清单（按严重度排序）+ 处理建议 + 局限性说明」
5. **要 Word 版**：报告先用 Markdown 落地，再用 `md-to-docx-cn-report` 技能转 `.docx`
   （`python <该技能>/scripts/md2docx.py 报告*.md`）。不要手搓 docx。

耗时参考：19 家单位 / 约 34 人 × 2 轮 ≈ 68 次请求，约 **4～6 分钟**（服务器较慢，单次 1～2.5 s）。
**务必后台跑**，并带上 `cache.json`（脚本自动缓存，重跑不重复请求）。

## 报告必备章节

1. 检查依据与数据来源（法规 + 平台 URL + **核查方法说明**）
2. 检查结论摘要（一张表：总包/分包的配备率与问题数）
3. 项目经理配备核查（逐项目表格：单位/合同类型/项目经理/本单位注册/B 证/判定）
4. 安全员配备与所属单位核查（逐项目表格：单位/类型/在册人数/应配标准/名册安全员/持本单位有效证/判定）
5. 问题清单（编号、项目、单位、问题、**对应条款**）+ 处理建议
6. **核查说明与局限性** —— 必须写明：平台结果不含身份证号，同名同姓风险；
   在册人数口径偏大属从严判定；建筑面积缺失导致总包档位未定；最终定性须结合原始凭证

## 语气与结论尺度

- 平台「查无记录」只能得出**「该企业名下无持证记录」**，不能直接定性为挂靠 ——
  要提示「建议调取身份证原件核对后定性」。
- 超龄（≥60 岁）、证书临近到期（3 个月内）要单独列为风险项。
- 把「程序性缺失」（未配备）与「实质性问题」（证在他单位、无证）分级，
  按严重程度排序，别把二者混在一张表里。
- **按项目拆报告时，每份要自包含**：项目基本情况 → 检查依据与数据来源 → 项目经理核查 →
  安全员核查 → 花名册基础数据核查 → 问题清单 → 处理建议 → 核查说明与局限性。
  用户常会拿单份报告去做单个项目的整改通知，缺章节会不好用。

## 两个必踩的计算坑（实测算错过）

1. **年龄必须从身份证第 7–14 位现算**，不要凭印象或从别的字段推断。
   本次曾误把某项目经理写成 60 岁，回查其身份证第 7–14 位是 `19860911`，实为 40 岁。
   一律用「出生年月日 + 检查日」现算，别目测。
2. **算「达标率」时先剔除不适用单位**。监理/咨询单位**不适用**第二十六、二十七条，
   分母要用「**有配备义务的单位数**」，不是全部单位数。
   例：4 家单位里 1 家是监理 → 分母是 3，达标率 = 1/3 = 33%（**不是 1/4 = 25%**）。

## 本机注意

- Python：`C:\Users\admin\.workbuddy\binaries\python\envs\default\Scripts\python.exe`（已装 `pypdf`）
- 输出中文记得 `PYTHONIOENCODING=utf-8`，否则 GBK 控制台会 `UnicodeEncodeError`
- 模块级不要无条件 `sys.stdout = TextIOWrapper(...)`，被 import 时会关闭 stdout —— 放进 `if __name__ == '__main__'`，
  并加 **`write_through=True`**，否则重包后的 stdout 是块缓冲，长任务全程看不到进度。

### 长任务会被回收 —— 务必这样跑

**后台任务在 Bash 工具调用返回后会被终止**（实测：`run_in_background` / `&` 起的进程，
只要工具调用链一空闲就消失，日志停在一半且无报错）。所以：

1. **不要用 `run_in_background` 跑这个脚本**，改用「单次工具调用内 `sleep` 轮询」的方式守着它跑完：
   ```bash
   python market_check.py <目录> out.json > run.log 2>&1 &
   for i in $(seq 1 60); do grep -q "完成 →" run.log && break; sleep 10; done
   tail -20 run.log
   ```
2. `cache.json` **每个单位处理完就落盘**，所以中断后用**同一条命令重跑**即可续跑，已查过的不会重复请求。
3. 全量请求量参考：19 家单位 / 34 人 ×（2 次企业过滤 + 最多 6 次同名翻页）≈ 270 次请求，
   服务器单次 1～2.5 s，**完整跑一轮约 8～12 分钟**。有缓存时数分钟内可完成。
